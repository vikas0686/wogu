# WG011 — I/O or blocking calls inside Workflow.sideEffect()

| | |
|---|---|
| **Rule ID** | WG011 |
| **Category** | Determinism ([WG001–WG099](../../CONTRIBUTING.md#rule-numbering)) |
| **Severity** | ERROR |
| **Engine** | Temporal Java SDK |
| **Since** | 1.0.0 |
| **Auto Fix** | Not Available |

## Problem

Code inside the callback passed to `Workflow.sideEffect(...)` or
`Workflow.mutableSideEffect(...)` — or any code reachable from that callback, however many
method calls away — performs I/O: opening a network socket, reading or writing a file,
making an HTTP call, querying a database, or invoking a method reflectively.

## Why this matters

`Workflow.sideEffect()` and `Workflow.mutableSideEffect()` exist to let a workflow perform
a small, local, non-deterministic computation exactly once and have Temporal record the
result in workflow history, so replay reuses the recorded value instead of re-running the
computation. They are the SDK's designed escape hatch from determinism rules like
[WG001](WG001.md) — reaching for one to "fix" a determinism violation is common, and mostly
correct, for something like a locally-computed UUID or a coin-flip.

It is not a safe escape hatch for I/O. The callback still runs synchronously on the
workflow thread, on the same code path as the rest of the workflow task: unlike an
Activity, it is never retried independently on failure, is never heartbeated to signal
progress on a long-running call, and a failure inside it fails the entire workflow task
rather than being handled as a scoped, retryable error. Code that "fixes" a determinism
problem by moving I/O into a `sideEffect` callback trades a replay bug for an availability
bug, and it's easy to not notice the trade was even made.

## Bad Example

```java
public class PaymentWorkflowImpl implements PaymentWorkflow {
  @Override
  public String lookUpAccountTier(String accountId) {
    return Workflow.sideEffect(String.class, () -> {
      // A real HTTP call, executed synchronously on the workflow thread, with no
      // Activity retry policy or timeout behind it.
      return pricingClient.send(pricingRequest(accountId)).body();
    });
  }
}
```

This is flagged even when the I/O is behind a helper method the callback delegates to,
several calls away from the `sideEffect` call site itself:

```java
public class PaymentWorkflowImpl implements PaymentWorkflow {
  private final PricingService pricingService = new PricingService();

  @Override
  public String lookUpAccountTier(String accountId) {
    // WG011 still fires: WoGu's call-graph analysis follows this call into
    // PricingService.fetchTierLabel() and finds a FileReader constructed inside it.
    return Workflow.sideEffect(String.class, () -> pricingService.fetchTierLabel());
  }
}

class PricingService {
  String fetchTierLabel() {
    try (FileReader reader = new FileReader("/etc/wogu/pricing-tiers.conf")) {
      return "loaded";
    } catch (Exception e) {
      return "default";
    }
  }
}
```

## Good Example

```java
public class PaymentWorkflowImpl implements PaymentWorkflow {
  private final PricingActivities pricingActivities =
      Workflow.newActivityStub(
          PricingActivities.class,
          ActivityOptions.newBuilder()
              .setStartToCloseTimeout(Duration.ofSeconds(10))
              .setRetryOptions(RetryOptions.newBuilder().setMaximumAttempts(5).build())
              .build());

  @Override
  public String lookUpAccountTier(String accountId) {
    return pricingActivities.fetchTierLabel(accountId);
  }
}
```

## Recommended Fix

Move the I/O into an Activity with a real `ActivityOptions` timeout and retry policy, and
call it directly from workflow code the normal way. Reserve `sideEffect()`/
`mutableSideEffect()` for values that genuinely need no I/O at all — a locally-generated
UUID, a coin-flip, reading an in-memory cache already populated by the worker process.

## False Positives

WG011 reuses the same call-graph engine as every other Determinism rule, with one
difference: instead of firing on a matching call anywhere reachable from a workflow entry
point, it only fires on a match found inside a `Workflow.sideEffect(...)`/
`Workflow.mutableSideEffect(...)` callback specifically — the same
[`ExecutionContext`](../call-graph-analysis.md) tracking WG001 already uses to *exclude*
`sideEffect` callbacks (via `suppressedContexts`), applied in the opposite direction (via
`requiredContexts`) to *only* flag inside them.

The I/O calls WG011 recognizes are a deliberately representative starting set — common
network, file, JDBC, and reflection APIs — not an exhaustive list of every blocking call in
the JDK or in common libraries. A network or file operation from a library WG011 doesn't
yet know about will not be flagged; this is a false negative, not a false positive, and the
list can grow over time the same way any `forbidden-method` rule's `methods`/`constructors`
list can.

As with every call-graph-based rule, this analysis intentionally stops, without reporting
anything past that point, at a call it cannot resolve to source it can see — most notably,
a callback passed as a **method reference** (e.g. `Workflow.sideEffect(Type.class,
this::doSomething)`) rather than written inline as a lambda at the call site: WoGu's
call-graph traversal only follows calls it can resolve, and `Workflow.sideEffect(...)`
itself never resolves to project source (it's the real Temporal SDK method), so nothing
creates a call-graph edge into a method reference's body at all. If you believe WG011 is
flagging or missing something incorrectly, please open an issue with a minimal
reproduction.
