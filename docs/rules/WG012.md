# WG012 — MutableSideEffect with reference-equality value type

| | |
|---|---|
| **Rule ID** | WG012 |
| **Category** | Determinism ([WG001–WG099](../../CONTRIBUTING.md#rule-numbering)) |
| **Severity** | WARNING |
| **Engine** | Temporal Java SDK |
| **Since** | 1.0.0 |
| **Auto Fix** | Not Available |

## Problem

A `Workflow.mutableSideEffect(id, valueClass, updateFunction, func)` call's `valueClass`
argument names a type that relies on inherited, identity-based `Object.equals()` instead of
a real, value-based one.

## Why this matters

`Workflow.mutableSideEffect()` records a new history event only when its `updateFunction`
reports the value as changed — that's the entire point of the API over a plain
`sideEffect()`: skip recording (and skip re-running `func`) when nothing actually changed.
The common `updateFunction` pattern is `(oldValue, newValue) -> !oldValue.equals(newValue)`,
which delegates the "did it change" question straight to `equals()`.

A value type with no `equals()` override falls back to `Object`'s default, which compares
object identity, not field values. Since `func` constructs a *new* instance on every call,
two logically-identical values are still two different objects — `equals()` always returns
`false`, `updateFunction` always reports "changed," and every single call appends a new
`MarkerRecorded` event to workflow history regardless of whether the underlying value moved
at all. `mutableSideEffect()` silently degrades into `sideEffect()` with extra bookkeeping
overhead, and a workflow that calls it frequently accumulates history far faster than its
author likely expects.

## Bad Example

```java
public class PaymentWorkflowImpl implements PaymentWorkflow {
  @Override
  public String fetchCurrentPrice() {
    Price price = Workflow.mutableSideEffect(
        "price",
        Price.class,
        (oldValue, newValue) -> !oldValue.equals(newValue),
        () -> pricingService.currentPrice());
    return price.toString();
  }
}

class Price {
  // No equals()/hashCode() override — every call is reported as "changed."
  double amount;
}
```

## Good Example

```java
public class PaymentWorkflowImpl implements PaymentWorkflow {
  @Override
  public String fetchCurrentPrice() {
    Price price = Workflow.mutableSideEffect(
        "price",
        Price.class,
        (oldValue, newValue) -> !oldValue.equals(newValue),
        () -> pricingService.currentPrice());
    return price.toString();
  }
}

record Price(double amount) {
  // A record: the language always synthesizes a value-based equals()/hashCode(), so
  // updateFunction correctly reports "unchanged" once the price stabilizes.
}
```

A hand-written `equals()`/`hashCode()` pair (or a primitive/JDK wrapper type like
`Integer`/`String`) is equally correct — the rule only cares that *some* value-based
equality exists, not how it's implemented.

## Recommended Fix

Use a primitive, a record, or a type with a proper value-based `equals()`/`hashCode()` for
the `mutableSideEffect` value type. WG012 checks the value type's resolved `equals()`, not
the `updateFunction`, so rewriting only the `updateFunction`'s comparison logic (e.g. to
compare fields directly instead of calling `equals()`) does not suppress this diagnostic —
the value type itself still needs real equality for WoGu to recognize it as safe.

## False Positives

Unlike WG001–WG011, WG012 isn't a call-graph reachability rule — it's a `Class<T>`
argument type check. WoGu resolves the value type via its symbol solver: a Java record is
always treated as safe (the language guarantees a synthesized value-based `equals()`); a
type declaring its own `equals(Object)`, or inheriting one from a resolvable ancestor other
than `java.lang.Object`, is also treated as safe.

A type WoGu cannot resolve — one that lives in a compiled dependency rather than the
project's own source, since `SourceRootParser` never includes the target project's compiled
classpath — is treated as "cannot determine," not a violation. This is a deliberate
false-negative-preferring choice, the same one every other rule in this catalog makes for
an unresolvable call: WG012 will not flag a well-known JDK type it happens to resolve via
reflection (`Integer`, `String`, and similar all have real `equals()` and are correctly
recognized as safe), but a type from a third-party library not on WoGu's own classpath will
silently not be checked either way.

WG012 only inspects the `valueClass` argument; it never looks at `updateFunction`. An
`updateFunction` written to compare fields directly instead of calling `equals()` may well
be correct at runtime, but WoGu has no way to verify that a given lambda actually implements
value equality correctly (a trivial or inverted comparator would look the same
syntactically), so this is not a check WG012 attempts — the diagnostic will still fire
until the value type itself has real equality.

If you believe WG012 is flagging or missing something incorrectly, please open an issue
with a minimal reproduction.
